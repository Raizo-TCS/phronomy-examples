# r8 unit 4 examples

Use core baseline `3c5fddcae31cc98f8e081feae9b955cf536e5834` plus the matching
unit 4 application package, with these examples applied to
`0370d09fb1608b9596e1803275f713b1a204af26`.

- Set `PHRONOMY_PATH` to the updated core and run `bundle install` in each example.
- `HandoffDemo.build_runner(persistence: stores)` takes the complete composition;
  Agents receive `stores.agent`, the HandoffRunner receives `stores.multi_agent`.
- Team uses `stores.multi_agent`. Durable Orchestrators also receive
  `coordination_store: stores.multi_agent` alongside their Agent store.
- SQL resource mapping adds `agent.retentions` and `agent.cancellations`.
  Example 09 provides a Rails schema migration, while existing execution data
  must be converted offline. Table creation alone is insufficient.

The runnable migration is `scripts/migrate_unit4.rb`. From example 30/31 run its
`export`, `convert`, `import`, and `verify` modes with `--quiescent`,
`SOURCE_DATABASE_URL` and a distinct `DESTINATION_DATABASE_URL`. Read the core's
`docs/migrations/r8-unit4.md` before changing an existing application database.
Only the import destination is written; conversion preserves old IDs/revisions,
result and context content, cancellation intent and unresolved external work.

The committed legacy fixture was generated by the unmodified unit 3 core and
SQLite adapter. `shared/fixtures/generate_unit3_snapshot.rb` records reproduction
requirements. Tests verify separate-connection readback, old result access,
knowledge/provenance preservation, corruption rejection and import rollback.

Run `bundle exec rspec spec` at the examples root, then `bundle exec rspec` in
example 30 and example 31. Example 31 requires an actual PostgreSQL database and
resets its test schema; use a dedicated test database. Its admission ordering,
lock-wait and durability checks cannot be replaced by SQLite results. The package
validation report records which database gates were executed in the build environment.
